# Minimal Design

将用户给出的需求或已有设计收敛为一篇核心设计文档。目标是让读者快速看懂实现方式、接口边界、数据关系和端到端流程，不重写成完整规格说明。

## 工作步骤

1. 从当前对话、输入文档和项目上下文提取已确认的目标、核心设计选择及必需组件。沿用已有结论，不臆造产品行为；仅在缺少信息会改变设计时标出简短假设。
2. 先写实现概述，控制在三到四行，直接说明主要机制、关键判断依据和输出/落点。
3. 用简短小节交代所需接口、数据库关系和主流程。只保留足以实现和评审的内容。
4. 按用户指定文件名和位置保存；未指定时沿用当前工作区合适的文档位置。完成后核对文档确实存在且内容满足用户的篇幅要求。

## 默认文档结构

```markdown
# <设计主题>（简版）

<三到四行实现概述>

## API
<接口路径或操作> | <用途>

## 数据库表关系
<一句话说明数据放在哪里；优先用一个 Mermaid ER 图表达表及关系>

## 主要流程
<一个 Mermaid 流程图或简短有序步骤>
```

按任务需要删减或调整小节；不要为了填满模板增加无关内容。

## 精简规则

- **API**：说明接口路径/操作和用途即可。默认不写完整 request/response JSON schema，不罗列枚举，不展开状态码、异常和错误处理；用户明确要求时再补充。
- **数据库**：优先用一张 ER 图说明核心表与关系，并用短句说明每张表的职责。默认省略逐字段类型、约束细节和完整 DDL；用户明确要求或关系无法表达清楚时再展开。
- **流程**：只画一条主要成功路径及必要分支，使用一个 Mermaid 图。避免把校验、重试、权限、审计等次要机制塞进主图，除非它们改变核心设计。
- **实现选择**：保留会影响功能正确性的关键区分或假设。例如内存告警使用的指标与 pprof 可诊断范围不同，就用一句话交代；不延伸成通用风险清单。
- **语气与长度**：用短句和常见词，避免重复解释、背景铺陈、通用安全注意事项和泛化异常章节。不得为了显得完整而重复用户已经知道的上下文。
- **依据**：忠实压缩来源材料。关键事实若来自外部资料，保留最必要的出处；不要增加未验证的细节。

## 完成标准

文档开头三到四行内能读懂主要实现方式；读者能从 API 小节知道如何控制功能，从 ER 图看懂核心数据关系，并从主流程图看懂一次操作如何完成。其余细节只在用户明确要求时加入。
