# 技术文档生产（tech-review）

## 输出契约

- 交付**一篇 Markdown 文件**（不是聊天里的长回复），默认命名 `<主题>-<类型后缀>.md`，后缀取 `使用指南` / `原理与实战` / `规范解读`。
- 保存位置：用户指定则从其指定；未指定则存到当前工作目录。
- 交付前必须通过 **Markdown 结构 lint** 与 **Mermaid 语法 lint**，两项退出码均为 0。
- 正文语言：中文叙述 + 英文技术标识符（命令、字段、类型、枚举一律 inline code）。

---

## 工作流

### Step 1 · 确认交付参数

从请求中提取四项，缺失就取默认值，**不要为默认值追问**：

| 参数 | 默认值 |
|------|--------|
| 主题（技术/工具/规范名） | 必填，缺失才问 |
| 读者深度 | 有运维/开发背景的工程师，讲清"为什么"但不科普基础概念 |
| 附加要求（篇幅、侧重章节、必须包含的内容、语言） | 无 |
| 输出路径与文件名 | 当前工作目录 + Step 3 决定的后缀 |

只有两种情形必须问用户：主题完全无法判断；用户物料互相矛盾。其余情况先做，做完在交付说明里写清假设。

### Step 2 · 取料

**优先顺序**：官方文档 / 规范原文 / RFC / 源码 > 厂商文档 > 高质量技术博客 > 社区问答。至少 2 个独立来源交叉验证关键事实（版本号、字段语义、默认值、限制）。

- 需要外部资料：用 `WebSearch` 定位，用 `WebFetch` 抓正文；查规范先找"最新稳定版本"，别引用过期草案。
- 用户给了文件：文本类直接 `Read`；`.pdf` 走 `workbuddy-pdf` 技能；`.docx/.xlsx/.pptx` 走 `workbuddy-office-routing` 对应技能。
- 建一张**取料清单**，缺项就补搜：

| 类别 | 必取内容 |
|------|----------|
| 定位 | 一句话定义、英文全称、解决的问题、当前版本/标准编号 |
| 用法/结构 | 语法格式、参数或字段全量清单、默认值、取值范围、单位 |
| 示例 | 官方最小示例、真实输出样例、边界/异常示例 |
| 约束 | 版本差异、平台差异、权限要求、性能上限、已知坑 |
| 生态 | 相关工具/框架/实现、官方链接 |

- 拿不到的不要编：显式写"公开资料未明确 / 实现相关"，或删掉该小节。
- 顺手记录所有来源 URL，供文末"参考资源"。

### Step 3 · 判定文档类型

先回答三个问题：

1. 读者读完要做的**动作**是什么？（用起来 → 工具使用；理解运转 → 系统机制；按规范实现/对接 → 规范协议）
2. 主题是**单个可操作对象**、**多组件协作关系**、还是**正式文本条款**？
3. 主题的名词形态：命令/文件/接口 → 工具；架构/机制/框架概念 → 机制；规范/协议/Schema → 规范。

| 类型 | 典型对象 | 读者核心问题 | 关键证据 |
|------|----------|--------------|----------|
| 【工具使用】 | `vmstat`、`snmpwalk`、`/proc/net/snmp`、某 SDK | 怎么用？参数啥意思？输出怎么读？报错怎么办？ | 参数表、输出样例、诊断建议、脚本 |
| 【系统机制】 | K8s CRD/Operator、调度器、存储引擎 | 是什么？为什么需要？怎么协作？内部怎么跑？ | 概念类比、组件拆解、架构图、实战跑通 |
| 【规范协议】 | STAC、OGC API、OTel、HTTP/2 | 字段必填吗？取值合法吗？版本差异？实现怎么落地？ | 规范条款、字段表、扩展机制、实现映射 |

**混合主题处理**：选"决定读者最终动作"的那个为主类型，另一类型作为其中一章（如"某规范 + 它的 CLI" → 主类型规范协议，附录工具清单；"某命令 + 它读的内核机制" → 主类型工具使用，第 4 章机制详解）。**只允许一个主类型**，不要两种骨架拼接。

### Step 4 · 载入范式并起草

判定类型后，**必须先读对应参考文件**再动笔：

- 【工具使用】→ `references/type-tool-usage.md`
- 【系统机制】→ `references/type-system-mechanism.md`
- 【规范协议】→ `references/type-spec-protocol.md`

按该文件的结构骨架排章节、按"各章写法细则"补内容、按"表达特征清单"过一遍。骨架的章节顺序不要重排；确有不需要的章节可删，但不要新增与骨架冲突的大章。

写作时的硬性要求：

1. 每章第一句先给结论/定位，再展开细节。
2. 属性类信息（参数、字段、状态、对比）一律用表，表 2~4 列。
3. 每个代码块前有一句中文引导，块内关键行有注释，示例可复制即执行。
4. 结论可判定：写"`RetransSegs`/`OutSegs` > 1% → 链路拥塞"，不写"要关注重传"。
5. 阈值、默认值、版本号必须带前提或来源；不确定就标"仅供参考"。
6. 术语首次出现给中英对照，之后全文只用一种叫法。
7. 不写开场铺垫（"本文将带你……"）、不写营销词（强大/优雅/非常简单）、不写空章节标题。
8. 占位符统一 `<UPPER>` 或 `{UPPER_SNAKE}`，首次出现处说明。
9. 重点判断用引用块统一格式：`> **关键认知**：` / `> **重要区分**：` / `> **选型直觉**：` / `> ⚠️ ……`。
10. 危险操作后紧跟影响与回滚方式。

### Step 5 · 画图（Mermaid）

**选型**：流程/架构 → `flowchart TD|LR`；组件交互/访问时序 → `sequenceDiagram`；状态机/生命周期 → `stateDiagram-v2`；数据模型 → `erDiagram`；层级分类 → `mindmap`；排期 → `gantt`。

**实测语法红线**（违反必报 parse error）：

| 写法 | 结果 | 正确做法 |
|------|------|----------|
| `A[文本(说明)]` | ✗ 报错 | 整体加引号：`A["文本 (说明)"]`（中文括号同理） |
| `A[文本 (说明)]` | ✗ 报错 | 同上，括号必须被引号包住 |
| `-->\|失败 (超时)\|` | ✗ 报错 | 标签加引号：`-->\|"失败 (超时)"\|` |
| `A --> end` | ✗ 报错 | `end` 是保留字，换节点 ID |
| `A->>B: 请求; 返回` | ✗ 报错 | 时序图消息文本不要用 `;`，改逗号或句号 |
| `A["含 \"引号\" 文本"]` | ✗ 报错 | 用实体 `#quot;` 或换单引号 |
| `subgraph 管理端 snmpwalk` | ✗ 报错 | `subgraph G1["管理端 snmpwalk"]` |

**推荐写法**：

- 首行必须声明图型；节点 ID 只用字母数字下划线，显示文本放括号里。
- 分层架构用 `subgraph ID["中文层名"]`，内部可加 `direction TB`。
- 边标签用动词（`定义`/`监听`/`调用`/`返回`），不要写"关系1"。
- 配色用 `classDef` 或 `style`，浅底深描边（`fill:#e3f2fd,stroke:#1976d2`），与浅色主题一致；禁止纯黑填充。
- 单图节点 ≤ 20 个；超过就拆两张。一篇文章 2~4 张图，图前有一句"这张图说明什么"。
- 图内文字与正文术语一致，不用缩写新造词。

### Step 6 · 自检与修复

```bash
python "<skill_dir>/scripts/lint_md.py" "<文档路径>"
node "<skill_dir>/scripts/check_mermaid.mjs" "<文档路径>"
```

`<skill_dir>` 为本 skill 目录，用户级安装时是 `~/.workbuddy/skills/tech-review`。首次运行 Mermaid 校验会自动安装 `mermaid`+`jsdom` 到 `~/.tech-review-lint`（约 30 秒，需 node ≥ 18）；若离线失败，脚本自动降级为启发式检查并提示，此时仍需人工复核图内特殊字符。

- 两条命令都必须 **exit 0**；有 `[ERROR]` 一律修，`[WARN]` 逐条判断（表前列空行、锚点失效、行尾空格这类直接修）。
- 修完**重新跑一遍**，直到干净。不要"改一处不重跑"。
- 额外人工复核三项：字段表是否都有单位/默认值；每个代码块是否可执行；每张图是否与正文一致。

### Step 7 · 交付

用 `present_files` 呈现 Markdown 文件，并在回复里给一段**不超过 12 行**的交付说明：

```text
类型判定：<类型>（依据：……）
结构：<主章节列表，一行>
资料来源：<n> 个，主要为 <官方文档/规范原文/…>
自检：lint_md 通过（0 错误 0 警告）；mermaid <n> 图通过
已知缺口：<没查到/未验证的点，没有就写"无">
```

若用户要求继续补充或调整，改文档后必须重跑 Step 6。

- [ ] 术语全文统一，中英对照只在首次出现
- [ ] 参考资源章节已列出来源链接
- [ ] 两项 lint 均 exit 0
