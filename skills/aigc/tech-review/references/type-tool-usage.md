# 【工具使用】类技术文档撰写范式

适用于：命令行工具、配置文件/伪文件（如 `/proc/*`）、接口/SDK、协议客户端工具、监控采集命令等
"读完能上手用、能判断输出对不对"的文档。

判定信号：主题是一个**可执行/可读取的具体对象**；读者的问题是"怎么用、参数什么意思、输出怎么读、报错怎么办"。

---

## 一、结构骨架（按此顺序，不随意增删）

| 序 | 章节 | 层级 | 写什么 | 篇幅占比 |
|----|------|------|--------|----------|
| 1 | 概述 | H2 | 一句话定位（英文全称 + 中文名）+ 解决什么问题 + 覆盖范围/环境前提 | 3% |
| 2 | 基本用法 / 文件结构 | H2 | 语法格式、参数表、最小可用示例 | 15% |
| 3 | 输出字段详解 | H2 | 真实输出样例 + 分板块字段表 + 每板块"诊断建议" | 30% |
| 4 | 核心机制详解（选 1 个） | H2 | 最易误解或最关键的字段/环节深挖 | 20% |
| 5 | 使用示例与实战脚本 | H2 | 可直接运行的脚本 | 15% |
| 6 | 常见应用场景 | H2 | 编号小节，每节一个可复制命令 | 10% |
| 7 | 注意事项 / 故障排查 | H2 | 注意事项表 + 错误信息表 + 排查流程图 | 7% |
| 8 | 参考资源（可选） | H2 | man page、官方文档、RFC | — |

> 第 1 章写在最前面的文档，第 1 章必须短：3~5 行讲清"这是什么、给谁用"。不要写"本文将介绍……"的铺垫。

## 二、各章写法细则

### 1. 概述

```markdown
## 概述

`vmstat`（Virtual Memory Statistics）是 Linux 下用于报告进程、内存、分页、I/O、CPU 活动快照的命令行工具，常用于快速判断系统瓶颈落在 CPU、内存还是磁盘。
```

- 格式：**对象名（英文全称）= 中文定性 + 典型使用场景**。
- 若主题是伪文件，先给"文件结构"再给字段：说明"标题行 + 数据行"配对、分隔符、单位、权限。
- 环境前提写清楚（内核版本、工具版本、发行版差异），一句话即可。

### 2. 基本用法

固定三段：

1. **语法块**：`命令 [选项] <必填参数> [可选参数]`，用方括号/尖括号表达可选与必填。
2. **参数表**：必须给"默认值"或"可选值"列，只列真正常用的，其余指向 `man`。

```markdown
|选项|说明|默认值|
|------|------|------|
|`-t`|添加时间戳|关闭|
|`-r`|重试次数|5 次|
```

3. **最小可用示例**：3~5 条命令，全部可复制执行，每条上方一行注释说明目的。

```bash
# SNMPv2c 基本用法
snmpwalk -v2c -c public 192.168.1.1

# 指定 OID 范围
snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2
```

### 3. 输出字段详解（本文档主体）

- 先贴**一段真实输出**（原样，不做美化），让读者建立形状感；必要时用注释标出关键列。
- 再**按输出板块分小节**拆字段，每个板块一张表：`|字段|含义|单位|说明|`。强调主字段时用 `**\`字段\`**` 或 ⭐。
- 每个板块表后必须接 **`**诊断建议：**`**，用"条件 → 结论"箭头句式，写可判定的结论而不是"需要注意"这类空话：

```markdown
**诊断建议：**

- `r` > CPU 核数 × 2 → CPU 可能是瓶颈
- `b` > 0 且持续增长 → I/O 或磁盘可能有问题
- `swpd` > 0 且持续增长 → 物理内存不足，系统开始 swap
```

- 字段表里出现专业名词，同步给判别标准（如 `ifOperStatus`：1=up，2=down）。
- 章节内部若有"最核心字段"，用一个引用块做导流，别在字段表里写长段落：

```markdown
> ⚠️ **`cs`** 字段是本文档的核心，详见 [上下文切换详解](#上下文切换cs详解) 章节
```

### 4. 核心机制详解（只写一个）

选题标准：读者最容易读错的那个字段/环节（`cs`、`InReasmFails`、`syncookiesSent`）。

固定推进链，每步一个 H3：

1. **是什么**：定义 + 一句话本质。
2. **做什么**：编号列出发生过程（1. 保存寄存器 2. 恢复寄存器 3. 更新调度器数据结构）。
3. **和相邻概念的区别**：对比表（`|项目|A|B|`）。
4. **正常范围**：阈值表（`|环境|数值|说明|`），并显式加 caveat："上述阈值仅供参考，实际值与 CPU 核数、负载类型密切相关，建议用每核均值判断。"
5. **来源/成因**：表（`|来源|说明|示例|`）。
6. **影响**：表（`|影响|说明|`）。
7. **排查步骤**：`**步骤1：……**` + 一条可执行命令，逐步收敛。
8. **优化方案**：表（`|方案|适用场景|操作方法|`），操作方法给具体命令。

### 5. 使用示例与实战脚本

- 脚本级示例用 `#!/bin/bash` 开头，含功能注释、变量集中定义、告警阈值判断。
- 脚本内关键行给中文注释；不写"伪代码"。
- 优先给"监控类"和"诊断类"两个脚本：前者持续采样，后者一次性输出结论。

### 6. 常见应用场景

编号小节（`### 1. 网络流量监控`），每节 1 个场景 + 1 个可复制命令块，不求全但求可操作。

### 7. 注意事项与故障排查

三件套：

- **注意事项表**：`|项目|说明|`，覆盖数据类型（累计 vs 瞬时）、位宽溢出、权限、版本差异、读取原子性。
- **错误信息表**：`|错误信息|可能原因|解决方案|`，错误信息用原文并加 inline code。
- **排查流程图**：`mermaid flowchart TD`，决策节点用菱形问句，末端节点用红/绿 style 标出"故障点/正常"。

## 三、表达特征清单（逐条自检）

1. 参数、字段、路径、命令、枚举值一律 inline code。
2. 属性类信息用表，不用长句罗列；表控制在 2~4 列。
3. 每个代码块前有一句中文引导；块内有关键注释。
4. 结论必须可判定："`RetransSegs` / `OutSegs` 比例过高 → 网络拥塞"，而不是"要关注重传"。
5. 单位、默认值、取值范围、合法枚举值必须出现。
6. 阈值必须带环境前提与"仅供参考"声明。
7. 占位符统一 `<>`（`<PID>`）或 `{}`（`{PRODUCT_ID}`），并在首次出现处说明。
8. 同一字段全文只解释一次，其余位置用锚点引用。
9. 中文叙述 + 英文标识符，不放英文整句。
10. 不写营销话术、不写"强大/优雅/非常简单"。
11. 危险操作（删除、重置、改内核参数）紧跟"影响 + 回滚方式"。
12. 版本敏感内容标注适用版本。

## 四、常见反例

| 反例 | 问题 | 改法 |
|------|------|------|
| 把 `man` 的参数表整段搬过来 | 无取舍、无优先级 | 只留常用项，给默认值与典型组合 |
| 字段表只有"含义"一列 | 无法换算、无法判断 | 补单位、默认值、取值范围 |
| 全是散文解释输出 | 查不动、扫不到 | 改表格 + 诊断建议 bullet |
| 代码块无注释、无引导句 | 读者不知道在干什么 | 前置一句"做什么"，块内注释关键行 |
| 阈值不给前提 | 换机器就错 | 写明核数/负载类型，给比值而非绝对值 |
| 报错章节只写"检查配置" | 无法执行 | 明确查什么文件、什么命令、看哪个字段 |
