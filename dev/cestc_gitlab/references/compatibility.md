# glab 与 GitLab 实例兼容性恢复

只有复现了真实的 API/协议不兼容才进入此流程。更新提示、较旧的发布日期、单个高层子命令缺失、资源级 404、无权限 403 或普通参数 422 都不足以证明版本冲突。

## 诊断与选型

1. 保存不含凭据的证据：`glab version`、`glab api --hostname code.cestc.cn version`、失败命令、HTTP 状态和错误文本。
2. 分别验证 `/user`、`/version` 和一个确定可访问的项目读取。区分：
   - **认证/权限问题**：修复登录、token scope 或项目权限，不换 CLI 版本。
   - **高层命令能力缺口**：改用 `glab api`，不必安装。
   - **实例不支持该功能**：更换 CLI 也无法增加服务端功能，改用实例支持的 API 或说明限制。
   - **协议/API 兼容冲突**：例如 CLI 明确报告不支持该 GitLab 版本，或官方兼容性资料能解释已验证请求的系统性失败。进入安装步骤。
3. 根据实例版本、失败接口和 `gitlab-org/cli` 官方发布说明选择兼容版本。glab 与 GitLab 没有相同版本号的一一对应关系；`glab check-update` 只能说明有更新，不能证明兼容或不兼容。无法从可靠资料确定版本时，向用户说明证据并请求选择，不随机升降级。

## 安装与验证

用户已授权在确认冲突后安装相应版本。直接完成安装，不停留在建议：

1. 保留当前可执行文件和配置，从 glab 官方发布渠道取得选定版本。优先安装到用户目录下的隔离工具目录；只有用户明确要求时才全局替换或使用管理员权限。官方提供校验值或签名时先验证。Windows 可用 `winget show --id GLab.GLab --versions` 查候选，但包管理器无法固定所需版本时改用官方归档。
2. 新二进制沿用现有 glab 授权配置，不复制或打印 token。分别执行：

   ```bash
   <新glab路径> version
   <新glab路径> auth status --hostname code.cestc.cn
   <新glab路径> api --hostname code.cestc.cn user
   <新glab路径> api --hostname code.cestc.cn version
   ```

   新二进制未识别授权时，让用户通过它交互执行 `auth login --hostname code.cestc.cn`。
3. 先重放原来失败的只读请求。确认恢复后，在本任务后续命令中使用该二进制；文件脚本用 `--glab <新glab路径>`，其他命令可直接写完整路径，或设置 `GLAB` 供脚本使用。
4. 若原失败操作是写请求，先读取资源判断它是否已经生效，再决定是否重放。最后报告旧版本、新版本、实例版本、安装位置和验证结果。隔离安装未改变系统默认 `glab` 时要明确说明。

完成标准：选定版本有官方兼容性依据，新 CLI 的授权与 `/version` 均验证成功，原冲突请求通过只读重放或状态核对确认恢复。
